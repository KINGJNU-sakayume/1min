## 2. 바꿔야 했던 지점과 이유

1. **정각 전 입력 라우팅** (`reducer.ts`, 코어). M1은 PREROLL 동안 `openButton` 단계에만 입력을 보냈다. 수강신청은 정각 전에 *로그인*을 하고, 정각 전 신청은 "수강신청 기간이 아닙니다!"(S56)가 떠야 한다. → PREROLL 입력은 현재 단계 핸들러에 보내고 판단은 단계가 한다. 티켓팅 동작은 같다(`openButton`이 EARLY를 판단). 카드는 여전히 정각 뒤에만 돈다.
2. **새 단계 종류 `courseCart`** (`steps/courseCart.ts`). 과목별 상태 `idle → pending(서버 지연) → success | full | blocked`, 정각 전·지연 카드 중 `notPeriod`, 같은 시간표 칸 중복 불가(S59). 마감 틱은 "담은 인원/정원"으로 정해지고 화면에 숨는다(희망 인원 ≤ 정원이면 마감 없음, S59). 카드는 기존 `effect.hook` 메커니즘으로 연결(`courseCart.notPeriod`, `.slow`, `.lateFull`, `.blockNext`) — **카드 시스템 변경 없음**.
3. **디스패처 case 4곳** (`steps/index.ts`): init·input·tick·hook. kind를 switch로 묶어 둔 덕에 다른 곳은 손대지 않았다.
4. **솔버 봇 정책** (`bot/solver.ts`): 화면에 보이는 "담은 인원/정원"이 높은 과목부터, 시간표가 겹치지 않게 신청. 숨은 마감 틱은 보지 않는다.

## 3. 바꾸지 않아도 됐던 것 (일반성 증거)

- 디렉터(예산·램프·슬롯·쿨다운·상호배제·단계 기준 카드), 카드 수명·실패 효과·시너지
- 결과 규칙(`stat` 조건으로 `coursesFull`, `notPeriodHits` 등 새 카운터를 데이터만으로 사용)
- 리플레이·결과 해시·시드·파생 시드 재시도
- 공통 카드 5장(알림·보안문자·서버 지연·팝업 차단·광클)을 그대로 재사용
- 공통 테스트: `src/engine/stages.test.ts`가 **스테이지 목록을 돌며** 퍼징·솔버·리플레이를 검사하므로 새 스테이지는 자동으로 검증된다

## 4. 다음 스테이지를 위한 교훈

- 단계 종류가 늘면 `steps/index.ts`의 case가 늘어난다. 6~7종을 넘으면 kind→핸들러 테이블로 바꿀 것을 검토 (지금은 switch가 타입 안전성에 유리).
- 단계 간에 데이터를 넘길 일(예: 신청한 과목을 시간표 화면에 그리기)이 생기면 `RunState`에 판 단위 메모가 필요하다. 이번에는 통계 카운터(`creditsRegistered`)로 대신했다.
- 수강신청은 정각 직후 몇 초에 승부가 갈려 판이 짧다(밸런스 리포트: 솔버 약 6초). 기차표처럼 긴 스테이지와 섞어 라인업 리듬을 맞춘다.
